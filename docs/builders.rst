ビルダーと静的サイトの制約
==========================

MaatLog のサポート範囲は Sphinx のビルダーに依存します。ブログ機能一式（アーカイブ、
Theme API の検証、Atom フィード、MaatLog の HTML メタデータ注入）は、静的なマルチ
ページ HTML ビルダーに限定されます。

テストスイートが検証している HTML 以外の代表例には、``text`` と LaTeX ソースの生成が
あります。TeX ツールチェーンは MaatLog の依存関係ではありません。LaTeX ビルドは
PDF の生成ではなくソース生成を通じて検証しています。

部分的な HTML サポート
----------------------

別の HTML 形式のビルダー（例えば ``singlehtml``）が検出された場合、MaatLog は
``maatlog.builder.partial-support`` という警告を 1 度だけ出し、アーカイブ、
Theme API の検証、フィード、MaatLog の HTML メタデータ注入を **無効化** します。
それらのビルダーに対して、中途半端なアーカイブやフィードの出力が書き出されることは
ありません。

URI と出力
----------

* ページ内部の URI はアクティブなビルダーから取得します（``get_target_uri`` と
  Sphinx の相対 URI ヘルパー）。MaatLog は ``.html`` か末尾スラッシュかという規則を
  ハードコードしません。
* 生成されるアーカイブページは ``html-collect-pages`` を通じて出力されます。
* Atom フィードと MaatLog が所有するアーカイブ HTML のパスは、``build-finished`` の
  成功時にコミットされます。所有権のマニフェストは **ページ** 用と **フィード** 用に
  分かれており、一方のクリーンアップが他方を削除することはありません。
* アーカイブとフィードのライターは、並列のドキュメント読み込みがマージされた後、
  メインプロセスの単一ライターとして実行されます。したがって直列ビルドと並列ビルドは、
  同等のアーカイブカード順序と同一の Atom バイト列を生成しなければなりません。

Sphinx の機能との共存
---------------------

同一プロジェクト内で次のものを混在させられます:

* 通常の ``.rst`` / ``.md`` ドキュメント
* reST と MyST の投稿
* ``autodoc`` / Python ドメインのページ
* ``:doc:``、``:ref:``、``:py:obj:``、および MaatLog のロール
* toctree と orphan ページ

MaatLog はドキュメントタイトル、検索インデックス、toctree、Pygments、画像ノード、
autodoc、intersphinx を置き換えません。標準の静的検索は Sphinx の HTML 検索のままで、
MaatLog は独自のインデックスやトークナイザを追加しません。

静的ホスティングの前提
----------------------

* HTML ビルダーの出力ディレクトリを静的サイトとしてデプロイします。
* フィードと canonical の絶対 URL が正しくなるよう、``html_baseurl`` に公開時の
  オリジン（およびパスのプレフィックス）を設定します。
* 公開境界を再現可能にするため、CI では ``SOURCE_DATE_EPOCH`` の利用を推奨します。
* env スコープの ``maatlog_*`` 設定を変更した場合は environment の再ビルドが必要です。
  フィード専用の設定は HTML を再ビルドします。

診断
----

公開される出力を曖昧にする契約違反（メタデータスキーマ、スラッグの重複、タクソノミー、
画像、Theme API、フィードの前提条件、安全でない出力パス）は、次の形式の構造化された
診断とともにビルドを失敗させます::

    <source>:<line>: ERROR: [maatlog.<code>] <summary>; field=<name>; value=<repr>; expected=<condition>

未解決の相互参照と、部分サポートのビルダーに関する通知は、通常の Sphinx の警告であり、
``-W`` のポリシーに従います。
